# ADR-0002：撮合引擎按交易对分片，只处理命令与事件，不持有余额

- 状态：已接受（2026-09-29）
- 关联：需求 §5.6、§5.7、§11.1、§11.2；决策 #22（合约复用现货引擎）

## 背景

撮合是延迟最敏感、正确性要求最高的组件。如果它同时负责余额校验和数据库写入，吞吐会被 I/O 拖垮，故障恢复也无法确定性重放。

## 决策

1. 引擎是独立 Go 进程，每个交易对一个分片，同一时刻只有一个活动实例（租约主备）。
2. 输入只来自 `order.commands`（分区键 symbol），先写 WAL 再处理；输出 `order.events` 与 `trade.events`，带分片内单调 `sequence`。
3. 引擎不查余额、不写数据库：下单前由 Spot Trading Service 同步调用 Ledger 冻结成功后才发命令；成交结算由 Ledger 消费成交事件完成。
4. 排序只依赖 sequence，不依赖墙上时钟；相同命令序列必须产生相同事件序列（确定性）。
5. 定期快照 + WAL 恢复；恢复期间交易对置 `CANCEL_ONLY`。
6. 合约撮合复用同一引擎代码，以独立分片部署，风控（保证金、强平）在引擎之外。

## 理由

内存订单簿 + 顺序处理是吞吐和确定性的来源；余额与撮合分离让两者各自可测、可重放。

## 后果

- 下单是异步确认（202），客户端以事件为准；撤单也是异步。
- 需要 Outbox 保证"冻结成功 → 命令发布"不丢失，需求 §11.1 已定义崩溃恢复。
- 引擎与账本之间存在短暂不一致窗口，通过对账兜底。

## 备选

数据库内撮合（SQL 锁竞争，吞吐低）；引擎内直接扣余额（单点持有资金状态，恢复困难）。
