# 阶段 2 压测报告（2026-09-29，升配前基线）

实施计划 §6.3 任务 12 的压测部分。目标（§6.2 阶段出口）：单交易对 ≥ 5,000 命令/秒、WebSocket 5,000 连接。用户决策：压测前再升级测试服或临时开压测机。**本报告是在未升级的测试服上测得的基线**，用来确定瓶颈和升级后要复测什么。

## 环境

- 测试服 t2.medium（2 vCPU、4 GB 内存、2 GB swap），PostgreSQL、Redis、Redpanda、ClickHouse、nginx 与 15 个应用容器全部在这一台上。
- 压测工具 `cmd/loadgen`（随应用镜像构建），在服务器上以容器运行、接入 compose 网络，绕过 Cloudflare 与网关的每 IP 配额（每 IP 每分钟 1200 次请求，单机从外面最多约 20 次/秒）：

```bash
ssh exchange 'cd /opt/exchange/infra && sudo mkdir -p /tmp/lg && sudo chown 10001 /tmp/lg && sudo docker run --rm --network exchange-infra_exchange --env-file apps.env -v /tmp/lg:/lg exchange-app:latest /app/loadgen users --count 40'
```

```bash
ssh exchange 'sudo docker run --rm --network exchange-infra_exchange -v /tmp/lg:/lg exchange-app:latest /app/loadgen orders --rate 100 --duration 30s'
```

```bash
ssh exchange 'sudo docker run --rm --network exchange-infra_exchange --add-host astras.vip:<nginx 容器 IP> exchange-app:latest /app/loadgen ws --url ws://astras.vip/v1/ws --header "X-Forwarded-Proto: https" --conns 5000 --ramp 19 --duration 60s'
```

  - `users`：经网关注册用户（开发收件箱取验证码、人机验证绕过令牌），等欢迎资金到账，写出用户 ID。
  - `orders`：按固定速率直接向 spot-trading-service 下 ETH-BTC 限价单（身份放 `X-User-Id`，与网关转发的一样），买卖交替、同价交叉，每两单成交一笔；报告受理延迟、撮合引擎在排空前的命令吞吐（`matching_commands_total`），结束时撤掉剩余挂单。`--engine ""` 不看引擎、`--drain 0 --cancel=false` 留下积压。
  - `ws`：持有 WebSocket 连接、订阅 BTC-USDT 的 ticker/depth/trades、应答心跳；报告建连、掉线与消息数。
  - 请求带 198.18.0.0/15（RFC 2544 压测地址段）内不同的 `X-Forwarded-For`，网关按每个地址单独计配额。
- 撮合订单簿的基准测试：`go test -bench BenchmarkBook ./internal/matching/domain`。

## 结果

### 下单全链路（受理 → 冻结 → Kafka → 撮合 → 成交 → 订单更新、结算、行情、分析）

| 目标速率 | 实际 | 受理（202） | 受理延迟 p50 / p90 / p99 | 引擎 | 机器 |
|---|---|---|---|---|---|
| 100 单/秒 × 30 秒 | 97/秒 | 2,999 全部受理 | 0.7 s / 1.7 s / 2.5 s | 97 命令/秒，随到随处理 | 负载 6.3 |
| 100 单/秒 × 30 秒（复测） | 96/秒 | 2,999 | 1.2 s / 2.5 s / 3.2 s | 93 命令/秒 | PostgreSQL 约 0.8 核，账本 0.28 核，交易 0.25 核，ClickHouse 0.19 核 |
| 150 单/秒 × 30 秒 | 107/秒（271 单因工作协程全忙跳过） | 4,228 | 4.2 s / 5.7 s / 6.1 s | 104 命令/秒 | CPU user 54%、system 27%、iowait 3%、idle 9%，steal 0 |

**这台机器上全链路约 100–110 单/秒就饱和**，瓶颈是 CPU：每单在受理、冻结、成交后的订单更新、结算（每笔成交三条分录）、行情与 ClickHouse 写入上都要占 CPU，而所有组件共用 2 个 vCPU。

### 受理本身（撮合暂停时）

撮合引擎 `docker pause`，下游没有成交要处理：100 单/秒持续 60 秒，5,999 单全部受理，**p50 10 ms、p90 22 ms、p99 81 ms**。说明受理与冻结路径本身不慢，全链路延迟来自下游处理与受理争用 CPU。

### 撮合引擎吞吐（排空积压）

引擎暂停期间积压命令，恢复后看 `matching_commands_total` 的增长（每批 500 条命令一个事务，写 WAL 与 outbox）：

| 积压 | 排空用时 | 平均 | 最高 1 秒 |
|---|---|---|---|
| 5,999 条（产生 2,995 笔成交） | < 2.3 s | > 2,600 条/秒 | — |
| 8,015 条 | 约 3.4 s | 约 2,400 条/秒 | 约 3,400 条/秒 |

订单簿本身（内存，不含持久化）：`BenchmarkBook` 在 Apple M1 Pro 单核约 **850,000 命令/秒**（每轮一笔交叉单、一笔挂单、一笔撤单，双边各 200 档）。引擎的上限在 PostgreSQL 写入与共享 CPU，不在撮合逻辑。

### WebSocket

| 连接数 | 路径 | 结果 | 网关内存 |
|---|---|---|---|
| 500 | 直连网关 | 0 失败、持有 30 秒 0 掉线 | 43 MiB |
| 2,000 | 直连网关 | 0 失败、持有 40 秒 0 掉线 | 124 MiB |
| 5,000（扩容前） | 经 nginx | 1,200 条成功后其余 429：同一来源 IP 每分钟 1200 次的配额（握手也计数，属预期）；且 nginx 默认上限约 1,000 条 | — |
| **5,000（扩容后）** | 经 nginx，每秒 19 条（不超单 IP 配额） | **0 失败、持有 60 秒 0 掉线**，建连 p99 5 ms | **329 MiB**（约 64 KiB/连接），nginx 180 MiB |

行情清淡（BTC-USDT 只有做市报价、无成交），5,000 条连接合计每秒约 450 条消息。

## 压测发现并已修复

1. **nginx 连接上限**：镜像默认每 worker 1024 个连接、2 个 worker、1024 个文件描述符，每条代理的 WebSocket 占两个连接，公网入口最多约 1,000 条 WebSocket。仓库里加了 `deploy/compose/nginx/nginx.conf`（`worker_connections 16384`、`worker_rlimit_nofile 65536`，compose 加 `ulimits`），CI 的 `nginx -t` 用它。
2. **网关内存**：每条连接约 64 KiB，原 192 MiB 上限约 3,000 条就会被 OOM；改为 512 MiB（`GOMEMLIMIT` 440 MiB）。
3. 故障注入顺带发现：参考行情流在网络静默丢包时要等 TCP keepalive 才发现断线，已加 30 秒空闲超时（见 `docs/runbook/testing.md`）。

## 正确性

两轮下单压测共约 24,000 单、12,000 笔成交之后：账本对账 7 项全部 0 差异（含成交已结清、成交编号连续、`TRADE_SETTLE`/`TRADE_FEE` 与成交一致），没有 FAILED 的结算，压测用户的订单全部终态（FILLED 24,028、CANCELED 95、REJECTED 98——后者是同一用户两单相遇时的自成交保护 `ORDER_SELF_TRADE`，符合设计）。撮合暂停时每用户最多 200 个未完成订单（`ORDER_TOO_MANY_OPEN`），符合设计。

## 与目标对照

| 目标 | 现状（t2.medium） | 结论 |
|---|---|---|
| WebSocket 5,000 连接 | 5,000 条经 nginx 持有 60 秒 0 掉线 | **达到**（需上面的扩容配置，已部署） |
| 单交易对 ≥ 5,000 命令/秒 | 撮合引擎排空约 2,400–3,400 命令/秒；全链路约 100 单/秒 | **未达到**，受 2 vCPU 共享限制 |

## 升级后复测

**用户 2026-09-29 决定：只有测试服，不升级、不复测**，下面留作以后需要时的参考。复测需要在 AWS 升级实例或临时开压测机。建议：

- 至少 4–8 vCPU 的非突发型实例（如 c6i/c7i.xlarge–2xlarge），或把 PostgreSQL、ClickHouse 放到独立实例；压测机与被测机分开，避免压测进程抢 CPU。
- 复测顺序：`loadgen orders` 逐级 200/500/1000/2000 单/秒各 60 秒，记录受理延迟与各消费组 lag；引擎排空测试用 50,000 条积压；WebSocket 在有成交的行情下测 5,000 条的消息扇出。
- 可能的优化方向（按预期收益）：交易服务消费 `order.events` 改为按批处理（现为逐条事务）；结算已是按批，可调大批量；分析写入与行情推送和核心链路错峰；PostgreSQL `synchronous_commit`、`wal_buffers` 与连接数调优。
