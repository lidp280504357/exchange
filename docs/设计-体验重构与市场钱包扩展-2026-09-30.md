## 1. 目标与范围

用户原话：页面不管前端还是后台都很 low、不连贯、卡；PC 网页版和手机 H5 做成两套，按二级域名区分；内容、动画、元素要多些；市场至少支持主流前 50 的币，能看 K 线、下单；充值接第三方平台（U盾），不自己接链，目前只能充 USDT、ETH、BTC；USDT 不管哪条链在平台里都是一个 USDT，提现时选链；ETH 与 BTC 各走自己的链。

拆成四条主线：

| 主线 | 目标 | 不做 |
|---|---|---|
| A. 前端重构 | 三个应用：**PC 站** `astras.vip`、**手机站** `m.astras.vip`、**管理后台** `admin.astras.vip`；用户站共用一套设计系统、组件库与数据层，后台可以有自己的视觉设计（基础组件可共用）；连贯的导航与页面骨架；流畅的实时更新（性能预算 §12）；完整的加载/空/错误态；一致的数字与时间格式；中英文完整覆盖；有内容、有动效（首页、行情榜、币种页、公告与帮助、价格闪动、深度条、底部抽屉、骨架屏、过渡动画） | 不做原生 App，不做 Tauri，不做一套响应式兼容两端 |

## 2. 现状结论（详见附录）

用户站与后台的卡顿根因、不连贯根因在附录 A；后端能力与缺口在附录 B。决定设计方向的几条：

- **卡**：订单簿每秒最多 10 次全量重建与重排序（`web/h5/src/lib/market.ts:98-105`）；每条私有推送都触发多次 REST 重拉（`Layout.tsx:29-58`）；全站没有 memo、节流或按帧刷新；行情/交易/合约页之间切换会断开并重连 WebSocket、销毁图表重拉 300 根 K 线；同一 `/v1/ws` 开了两条连接；没有代码分割，登录页也加载图表库；源站 nginx 没开 gzip。
- **不连贯**：没有设计令牌，品牌色硬编码 20 处，图表涨跌色与表格涨跌色不一致；至少 5 种 tab 样式、5 处手写 `<select>`；后台是另一套浅色组件；加载态显示为"暂无数据"；时间一处 UTC 一处本地；数字精度按服务端返回原样显示；导航里没有交易、合约、充值、提现入口，整站限宽 1024 px。
- **后端能扩，但要先修**：参考行情限流器曾有"给已放弃的调用也占时间片"的 bug（`internal/marketdata/adapters/binance/binance.go`，**已在 88f0753 修复**，取消的调用不再占时间片），仍待做：先建流再回填、并发回填、429 退避与符号映射；做市是单协程串行遍历所有交易对；WebSocket 每连接 50 个订阅上限，行情页每币一个 ticker 频道，50 币刚好用完；USDT 只有 6 位小数，低价币无法定价；参考 K 线已能到达前端（`market.reference_kline` 开关），但 ticker、24h 统计没有参考来源。
- **钱包**：只有 EVM 单链。再起一条 EVM 链会出两个真问题：每网络独立的地址计数器配同一个 xpub，同一地址在 ETH 与 BSC 上属于不同用户；热钱包 nonce 表只按地址键控，两条链互相推高 nonce。TRON 与 BTC 完全没有；代币（USDT）的提现、归集、对账没有。

### 4.2 域名、部署与跨站

| nginx | 三个 server 块：`astras.vip` → `apps/pc/dist`；`m.astras.vip` → `apps/m/dist`；`admin.astras.vip` → `apps/admin/dist` 并反代 `/admin/v1/` 到 admin-service。用户站都把 `/v1/` 与 `/v1/ws` 反代到 `api-gateway:8080`，每个站点对 API 同源，不需要 CORS。后台域名加 Cloudflare Access（邮箱 OTP）或 nginx IP 白名单，二选一，另加管理员 TOTP 登录 |

### 4.3 数据层（packages/core）

**单一 WebSocket 客户端**（替换现在的 `lib/ws.ts` + `lib/market.ts` 两条连接）：

- 应用生命周期内只有一条连接，登录后在同一连接上发 `auth`，公共与私有频道复用。
- 订阅引用计数：组件 `useChannel(name)` 增减计数，计数归零后延迟 15 秒再退订，切页不重连、不重拉快照。
- 重连：指数退避 1s→30s，加 ±30% 抖动；重连后自动重放当前订阅集合；`AUTH_EXPIRED` 触发刷新令牌后重新 `auth`。
- 序号：深度与私有频道校验 `prev_seq`，不连续时进入"等待快照"状态（只发一次重订阅，期间不再触发），并在 UI 上标出"同步中"。
- 页面隐藏（`visibilitychange`）时暂停高频频道的处理（消息丢弃只保留最后一条），恢复后重新请求快照。
- 订阅上限：行情列表改用一个 `tickers` 频道（后端新增，§8.1），单个页面订阅数不超过 10。

**行情高频存储**（不进 React state）：

- 订单簿：每个 symbol 一个对象，买卖各一个按价格排序的数组，增量用二分插入/删除，O(log n)；快照直接替换。聚合精度在读取时按档位合并，只对前 N 档（PC 20 档、手机 12 档）计算。
- 最新成交：环形缓冲 60 条。
- ticker：Map<symbol, Ticker>，只在字段变化时打标记。
- 渲染：订阅方用 `useSyncExternalStore` 读取，存储每帧最多通知一次（`requestAnimationFrame` 合并），因此每秒最多 60 次渲染而不是每条消息一次；深度条宽度、价格闪动都基于"本帧 vs 上帧"的差异计算。
- 私有推送直接写入 TanStack Query 缓存（`setQueryData`）：余额推送更新余额条目，订单/成交推送更新对应列表项；只有 `resync` 才失效重拉，且 500 ms 去抖。

**格式化**：

- 所有金额、价格、数量都是字符串 Decimal；`formatPrice(symbol, v)` 按交易对 tick 位数，`formatAmount(asset, v)` 按资产精度，千分位可选，紧凑模式（1.2K/3.4M）用于列表；`font-variant-numeric: tabular-nums` 全站开启，数字不抖动。
- 时间：一律用 `Intl.DateTimeFormat` 带用户设置的时区（默认浏览器时区），图表时间轴与表格一致；相对时间（"3 分钟前"）用于通知与记录。
- 枚举：`enumLabel(kind, code)` 从 i18n 取，缺翻译时显示可读的兜底文案并在开发模式告警，不显示裸代码。

**状态三态**：每个数据区块都区分 `loading`（骨架屏）/`empty`（插画 + 引导动作）/`error`（原因 + 重试）；页面级请求并行发起，不等交易对列表。

### 4.4 性能架构

- 路由级懒加载：每个页面一个 chunk；图表库、二维码、表格库单独 chunk；首屏（行情列表）不含图表库。
- 首屏预取：`/v1/market/pairs`、`/v1/market/tickers` 在 `index.html` 里 `<link rel=preload>`。
- 列表虚拟化：行情列表、订单/成交/流水表、审计日志全部虚拟滚动。
- 图表：`lightweight-charts` v5，K 线用 `update()` 增量；历史向左滚动分页加载（后端 `before` 参数，§8.1）；切换周期只换数据不重建图表；指标（MA 7/25/99、EMA、VOL）在 Web Worker 里算，主线程只画。
- 动效只用 `transform`/`opacity`，禁止动画触发布局；价格闪动用 CSS class 切换加 `animation`，不用 JS 计时器；列表进入动画只对首屏可见行做；`prefers-reduced-motion` 时全部关闭。
- 生产构建去掉 sourcemap 公开、StrictMode 只在开发；`web-vitals` 上报到 `/v1/telemetry/vitals`（可选，先打到控制台）；CI 里跑 Lighthouse CI 对 PC 与手机各三页出分。
- 测量口径与预算见 §12。

### 5.3 动效规范

- 页面切换：内容区淡入 + 8 px 上移，200 ms。
- 列表：首屏可见行错峰淡入（每行 20 ms，最多 12 行）。
- 价格：列表里的价格上涨闪绿、下跌闪红，背景色 10% 起、600 ms 衰减，只闪变化的单元格；头部大号价格（交易页顶栏、币种页、手机交易页）不闪，文字色 150 ms 过渡，旁边一个小箭头指示最近一次涨跌（2026-10-01 用户反馈整块底色每秒闪一次）。
- 订单簿没有动效（2026-10-01 用户两次反馈"一闪一闪"）：
  - 行是按与价差的名次作 key 的固定槽位，档位进出只改文字，不挂载、不淡入；深度条不过渡；数量格不闪。
  - 最多每 250 ms 重画一次（币安深度每秒推 10 次）。
  - 默认聚合步长随价格取，即不小于价格十万分之一的最细一档（BTC 约 84,000 时为 1），用户的选择按交易对记在本机。
  - 小于显示精度的档位（会显示成 0.0000）并入外侧一档。
- 成交流水：新成交从顶部滑入 150 ms。
- 按钮：按下缩放 0.98；提交中显示进度条；成功后图标打勾 300 ms。
- 手机：底部抽屉弹簧动画（`motion` spring，stiffness 400/damping 40）、tab 左右滑动切换、下拉刷新。
- 首页：数字滚动（CountUp）、跑马灯、卡片悬停浮起（PC）。
- 骨架屏：闪光扫过 1.2 s 循环。
- 所有动效在 `prefers-reduced-motion: reduce` 下退化为无动画。

## 8. 行情、流动性与市场扩展

### 8.1 展示口径：全部币安（用户确认）

- 用户看到的 K 线、最新价、24h 统计、**盘口深度、成交明细**全部来自币安：现货用 `stream.binance.com`，永续用 `fstream.binance.com`。平台自身的挂单与成交不进入任何行情展示；用户只在"当前委托 / 历史委托 / 我的成交"里看到自己的订单与成交。
- 界面不出现"参考""来源"字样。
- 平台成交 K 线与内部深度继续生成，只供后台、对账与风控（内部主题 `market.depth.internal`、ClickHouse 报表）。

### 8.2 数据管道（market-data-service → Kafka → 网关 → 客户端）

| 数据 | 币安流 | 内部主题 → 客户端频道 | 频率 |
|---|---|---|---|
| K 线 | `<s>@kline_1m`，其它周期由 1m 本地聚合（避免 13 × 50 = 650 条流）；历史用 REST `klines` 分页 | `market.candle.events` → `candles:{s}:{i}` | 2/s |
| ticker | `<s>@ticker`（24h 开高低收量额、最新价） | `market.ticker.events` → `ticker:{s}`、`tickers` | 1/s |
| 深度 | `<s>@depth@100ms` 增量 + REST `depth?limit=1000` 快照，按币安官方流程（缓冲增量、拉快照、用 `U/u` 对齐）维护每符号完整本地簿；对外发前 200 档快照 + 增量 | `market.depth` → `depth:{s}`（快照 + 增量，seq） | 10/s |
| 成交 | `<s>@aggTrade` | `market.reference_trades` → `trades:{s}` | 按成交 |
| 永续 | `fstream`：`@kline_1m`、`@ticker`、`@depth@100ms`、`@aggTrade`、`@markPrice@1s` | 同上 + `mark-price:{s}`、`funding:{s}` | 同上 |

- 连接：每条组合连接最多 50 条流（币安上限 1024，分 4 到 6 条连接分散压力）；24 小时主动重连；ping/pong；断线 30 秒显示横幅；5 分钟按 `market.halt_on_feed_loss` 置 HALT 并告警，恢复后自动回 TRADING。
- 本地深度簿是引擎虚拟流动性（§8.3）与客户端展示共用的同一份数据。
- 永续的标记价与资金费率展示币安数据；平台强平计算沿用现有指数/标记价逻辑（同样以币安为源，差异很小），后台可看两者差值。
- 授权提醒：币安条款不允许商业交易服务使用其数据（ADR-0004）。学习前提下不阻塞；灰度门禁不变。

### 8.3 撮合：合并簿 + 虚拟参考流动性（house liquidity）

问题：展示的是币安簿，如果内部仍靠做市机器人挂真实订单，用户看到的深度与能成交的深度不一致；而且 50 币 × 每 500 ms 撤补 20 单的订单风暴会压垮引擎与账本。

设计：

1. 引擎为每个符号持有一份"参考簿"（来自 §8.2 的本地深度簿，经 `market.depth` 主题或直接订阅，延迟目标 < 200 ms）。参考簿的每一档都是虚拟挂单，对手方是系统账户 `HOUSE`（沿用现有 `MARKET_MAKER` 科目与账户）。
2. 撮合规则：进入的订单在"真实用户挂单 ∪ 参考簿档位"里按价格优先匹配，同价真实挂单优先；参考档位每档可成交量 = min(币安档位数量, 单档上限, HOUSE 该资产可用库存)。市价单沿参考簿逐档吃；限价单未成交部分挂入真实簿（不展示）。
3. 参考簿每次更新（100 ms）后，引擎检查真实簿里价格已被参考最优价穿越的挂单，按其限价成交，对手方 HOUSE。
4. 用户之间仍可互相成交（真实簿），只是不展示。
5. 成交事件与结算：沿用 `trade.events` 与 `TRADE_SETTLE`，maker 侧为 HOUSE。账本新增 `HOUSE_TRADE_SETTLE`：用户侧照旧（冻结 → 扣减/入账），HOUSE 侧直接动可用余额、不预冻结。HOUSE 库存规则：USDT、BTC、ETH 不允许为负，不足时该方向停止虚拟流动性并告警；47 个站内币允许 HOUSE 为负（平台铸造，写进 ADR-0013）。
6. 做市机器人（market-maker 服务）退役为"库存账户 + 参数"，不再挂单；其配置改为虚拟流动性参数：允许的符号、单档上限、单符号总敞口上限、总敞口上限。
7. 永续：derivatives 引擎同样接入币安永续深度作为虚拟流动性，HOUSE 的合约账户持有对手仓位；资金费按现有规则在用户与 HOUSE 之间结算。
8. 这是 B-book：平台承担价格风险且不对冲（用户已选择不对冲）。后台显示 HOUSE 每币敞口、浮动盈亏与库存水位；开关 `market.house_liquidity`（全局与按符号）可关闭，关闭后只剩真实簿。
9. 确定性与重放：参考簿更新作为引擎输入命令进入 `order.commands` 同一分区（`ReferenceBookUpdate`），WAL 与快照包含参考簿，重放结果一致。（实施细化见 ADR-0015：参考簿走单独主题 `order.references`，分区与 `order.commands` 相同，WAL 按应用顺序编号。）
10. **初期策略（用户确认：前期没有用户，全部以币安价格为准）**：纯 B-book。所有成交的对手方都是 HOUSE，用户之间不互相成交（开关 `market.internal_matching` 默认关，有真实用户后再开）。成交价一律为下单时刻的币安价格：市价单沿币安深度逐档成交；限价单若立即可成交，按币安当前价成交（用户得到不差于限价的价格），否则挂起，待币安价格触及其限价时按限价成交。真实簿在初期只承担"等待触发的限价单"的作用。
11. **杠杆与覆盖范围（2026-10-02 用户决定）**：永续合约最高杠杆 125 倍，风险限额阶梯按币安样式重排（名义 ≤ 5 万 USDT：125x、维持保证金率 0.4%；≤ 25 万：100x、0.5%；≤ 100 万：50x、1%；≤ 500 万：20x、2.5%；≤ 2000 万：10x、5%；≤ 5000 万：5x、10%；以上：2x、12.5%）。HOUSE 对手方覆盖全部交易对与全部合约（含 ETH-USDT-PERP），不保留任何只有用户对用户的市场；用户之间撮合待用户量达标后再开。

**托管方接口映射（优盾钱包网关，按公开文档 https://www.uduncloud.com/geteway-interface 整理，2026-09-30；实施时以用户拿到的正式文档为准）**

|---|---|---|
| 请求信封 | 全部 POST，四个顶层字段：`timestamp`、`nonce`、`sign`、`body`（JSON 字符串）；`sign = md5(body + key + nonce + timestamp)` 小写，顺序不能变；`merchantId` 在 `body` 里 | 适配器统一封装；`key` 即签名密钥，只在 `apps.env` |

| 回调 | POST 表单，同样四个字段 `timestamp`、`nonce`、`sign`、`body`（JSON 对象字符串），用同一公式验签。`body`：`address`、`amount`、`fee`（整数字符串，实际值 = 值 / 10^`decimals`）、`decimals`、`coinType`、`mainCoinType`、`businessId`（仅提现）、`blockHigh`、`status`、`tradeId`、`tradeType`、`txId`、`memo`。`tradeType` 1 = 充值、2 = 提现；`status` 0 待审核、1 审核通过、2 审核拒绝、3 交易成功、4 交易失败；提现最多两次回调（审核 + 结果） | `ParseCallback`：验签 + 时间戳 ±5 分钟 + 以 (`tradeId`, `status`) 幂等。充值：`status=3` → `CONFIRMED` 并入账（托管方已做确认数）。提现：0/1 → `SUBMITTED`（托管方审核中/已通过），2 → `FAILED` 解冻，3 → `CONFIRMED` 记 `txId` 并结算，4 → `FAILED` 解冻 |

**端口** `internal/wallet/ports.CustodyProvider`：

```text
CreateDepositAddress(ctx, userRef, asset, network) -> (address, memo)
ParseCallback(ctx, httpRequest) -> CustodyEvent{kind: deposit|withdrawal, providerTxID, providerRef,
    asset, network, address, memo, amount, txHash, confirmations, status, occurredAt}
SubmitWithdrawal(ctx, idempotencyKey, asset, network, address, memo, amount) -> providerWithdrawalID
GetWithdrawal(ctx, providerWithdrawalID) -> status, txHash, fee

GetBalances(ctx) -> map[asset]Balance                // 对账
```

适配器 `internal/wallet/adapters/custody/udun`（按托管方文档实现）与 `custody/mock`（本地开发与端到端）。`networks` 表增加 `provider`（`self` / `udun`）与 `provider_coin`，wallet-service 按网络选择自建适配器或托管适配器；现有 Sepolia 自建模式保留为 `self`，不再扩展。

**充值**：用户选币种与网络 → wallet-service 向托管方申请地址（每用户每网络一个，落库 `deposit_addresses.provider_ref`）→ 页面展示地址、二维码、最小额、确认数 → 托管方回调 `POST /v1/wallet/callbacks/udun`（nginx 只放行托管方 IP；验签；时间戳防重放；按 `provider_tx_id` 唯一约束幂等）→ 现有充值状态机 `DETECTED → CONFIRMING → CONFIRMED`（确认数来自回调）→ 账本 `DEPOSIT_CREDIT` → 推送 `deposits` 频道与通知。USDT 任一网络都记入同一 USDT 账户，记录里保留网络。每 5 分钟 `ListDeposits` 轮询核对遗漏回调。低于最小额、未支持代币由托管方规则处理，平台记入待处理科目。

**提现**：现有流程不变（限额、地址簿、冷却、step-up、风控评分、后台审批）→ `APPROVED` 后 wallet-service 调 `SubmitWithdrawal`（幂等键 = withdrawal_id）→ 新状态 `SUBMITTED`（等待托管方，含托管方自己的复核）→ 回调或轮询得到 `BROADCAST(txHash) → CONFIRMING → CONFIRMED` 或 `FAILED` → 账本 `WITHDRAW_SETTLE` 或 `WITHDRAW_UNFREEZE`。`SIGNING` 状态只在自建模式使用。手续费 = 托管方费率 + 平台加价，配置在网络行，展示给用户的是总额。

**站内地址**：托管方给我们的地址都在 `deposit_addresses` 里，现有 `INTERNAL_TRANSFER` 逻辑照旧。

**对账（替换自建模式的链上对账）**：每小时拉 `GetBalances`，按资产比较：托管方余额 ≥ 用户负债 + 待处理提现；差异超阈值告警并自动关闭该资产提现；托管方余额低于日均提现量的 2 倍告警运营补充。

**安全**：API 密钥只在 `apps.env`；回调验签 + 时间戳 + 幂等；托管方后台开启提现复核与 IP 白名单；平台后台审批保留；回调日志表 `custody_callbacks`（原始报文、验签结果、处理结果）供排障。

**数据库**：`networks` 增 `provider`、`provider_coin`、`explorer_tx_url`；`deposit_addresses` 增 `provider_ref`；`deposits` 增 `provider_tx_id`（唯一）；`withdrawals` 增 `provider_withdrawal_id`、`provider_status`、状态 `SUBMITTED`；新表 `custody_callbacks`；去掉只适用于 EVM 的 `0x` CHECK 约束。

### 10.2 通用规范

- **DataTable 标准**：服务端游标分页（每页 50）、列排序、筛选栏（可保存为视图）、列显示/密度、行按记录 ID 作 key（旧后台的 A1 已在 88f0753 修复，新 DataTable 保持此标准）、行点击打开右侧详情抽屉、批量选择只用于导出。
- **危险操作**：统一 `ConfirmDialog`：显示影响对象、要求理由（≥ 10 字）、二次确认词（如输入用户 ID 后 4 位）；冻结/拒绝/停用/开关变更/调账都走它；双人审批的操作显示审批状态时间线。
- **表单**：`Form` + zod；金额用 Decimal 字符串校验，不用 `Number()`。
- **展示**：枚举全部映射中文标签并保留代码 tooltip；金额千分位与精度；时间按管理员时区；错误提示中文 + 追踪 ID 可复制。
- **实时**：待审提现数、告警数用 SSE 或 15 秒轮询更新导航角标；列表页不再整表轮询，改为"有新数据"提示条点击刷新。
- **权限**：导航与按钮按角色过滤；无权限项隐藏而不是报错。
- **视觉**：可以独立于用户站设计（用户决定），但复用 `packages/ui` 的基础组件与表单/表格能力，避免再写一套。

## 13. 风险与未决

| 风险 | 应对 |
|---|---|
| 两套站点让页面工作量接近翻倍 | 页面骨架在应用内，其余全在共享包；先做 PC 再做手机，手机站复用 PC 的数据钩子与业务组件 |

| 合并簿 + 虚拟流动性是 B-book：平台承担价格风险且不对冲；展示与成交靠参考簿延迟 < 200 ms 保证一致 | HOUSE 敞口与库存上限、按符号开关、后台实时敞口与浮动盈亏；参考簿延迟超阈值时暂停虚拟流动性；学习前提下接受风险 |

| 币安符号更名、下架、流中断 | 映射表在数据库，后台可改；`market.halt_on_feed_loss` 自动 HALT 并告警 |
| 单机资源 | c5a.xlarge 目前 22 个容器占 2.5 GiB；币安 50 币行情管道与虚拟流动性上线后再看，必要时把行情服务拆到第二台 |
