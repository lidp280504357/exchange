## 4. 故障场景覆盖

| 场景 | 方式 | 结果 |
|---|---|---|
| Redpanda 停机 | `scripts/fault/redpanda-outage.sh` | 读接口可用；停机期间注册，恢复后事件补发，欢迎资金与欢迎通知各一次，无新增死信 |
| ClickHouse 停机 | `clickhouse-outage.sh` | 注册、欢迎资金、划转不受影响；恢复后用户事件与划转事件补齐且只写一次 |
| Redis 停机 | `redis-outage.sh` | 公开读与登录态请求放行（限流与吊销检查降级放行）；发验证码与密码登录 503 拒绝；恢复后正常 |
| PostgreSQL 重启 | `postgres-restart.sh` | 连接池自愈；同一幂等键重试只产生一笔划转；账本核对通过 |
| 事件处理失败、毒消息 | Kafka 集成测试 | 4 次退避重试后进死信；无法解码的直接进死信；死信可重放，只由原消费组处理 |
| 重复投递 | inbox 集成测试、故障注入 | 状态只变更一次 |
| 服务商故障 | notification 单测（测试替身） | 重试、切换、熔断、全部失败记死信事件 |
| 未覆盖（后续阶段） | — | 撮合主备切换、链重组、行情中断、消息乱序、压测（实施计划 §9.1 其余项） |

## 6. 资源评估（实施计划 §11"阶段 1 末评估资源占用"）

评估时（2026-09-28，运行约 16 小时）：负载 3.3–3.9（2 vCPU），内存可用约 1.9 GiB，磁盘 82%。原因与处理：

| 发现 | 处理 | 处理后 |
|---|---|---|
| ClickHouse 自身系统日志：`trace_log` 一天约 1 GiB；上千列的 `metric_log` 合并反复超内存失败（CPU 200–700%，错误日志 900 MB）；服务日志为 trace 级 | `deploy/compose/clickhouse/config.d/small-server.xml`：去掉 trace_log、metric_log 等诊断表（保留 query_log、part_log），日志 warning 级、100 MB × 3，内存上限为物理内存 30%；删除已有的这些表并清空日志 | ClickHouse CPU 约 3%，内存 746 → 272 MiB，负载降到 1 以下 |
| Docker 构建缓存约 9 GB | `server-update.sh` 每次部署后 `docker builder prune --keep-storage 3gb` | 回收 5.6 GB |
| Redpanda 每个分区的活动段预分配 32 MiB（近 100 个 topic 约 3.9 GB） | `topics.sh` 把 `segment_fallocation_step` 设为 4 MiB（对新段生效），重建 dev 命名空间的 topic | 3.9 → 2.3 GB |

处理后磁盘 50%，内存可用约 2.1 GiB，应用容器各占 6–16 MiB。结论：阶段 1 的全部服务在这台机器上余量充足；阶段 2 的撮合、钱包与压测仍按风险表的应对，在压测前升配为非突发型实例或拆出应用机。

## 8. 风险登记更新与下一阶段依赖

风险（相对实施计划 §11）：

- **测试服容量**：本次评估发现并消除了 ClickHouse 诊断日志与构建缓存两处主要消耗（§6）；阶段 2 压测前仍需升配或拆机。
- **可观测性缺位**：没有采集端时，故障只能由端到端测试、故障注入与人工巡检发现；告警规则已写好，接入采集端即可生效。
- **第三方脚本**：API 参考页从 jsDelivr 加载固定版本的 Redoc，浏览器按 SRI 哈希校验；H5 本身不依赖它。

阶段 2 依赖：

1. 风控服务的基础规则与 `risk.events`（§7 遗留）。
2. 钱包：Sepolia RPC（Alchemy，已有）、签名隔离（ADR-0003）、HD 派生与 xpub 管理。
3. 撮合：ADR-0002 的边界，WAL、快照与确定性重放。
4. 行情数据授权方案（ADR-0004），灰度前必须落地。
5. 测试服升配或拆分应用机（压测前）。
6. 采集端与告警接收（Grafana Cloud 或自建）。
